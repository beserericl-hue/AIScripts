# CR-042 — Public SSO API entry point

## Note on scope — this is a PUBLIC API

Per user clarification 2026-05-23 — "this api key will be a public api." That changes three things vs. a private MemberClick-only integration:

1. **Multiple integrators.** Each external system gets its own API key with its own scope, domain allowlist, rate limits, and audit log. MemberClick is consumer #1; future partners get keys without code changes.
2. **Published documentation.** The endpoint surface, request/response shapes, error codes, rate limits, and key-issuance process all live on a public docs page (and as an OpenAPI 3.1 spec) so a partner's engineering team can integrate without back-and-forth with CSHSE.
3. **Versioning discipline.** Public endpoints are versioned in the URL (`/api/v1/auth/sso-login`) and follow a documented deprecation policy. Breaking changes mean a `/v2/` sibling — never an in-place rewrite.

The rest of this CR is unchanged in its core design (the ticket flow + direct flow + key model are all correct as-is), but the public-API requirements added below are mandatory before any external partner — including MemberClick — calls into production.

## Two problems, one solution

### Problem A — CSHSE has no federated entry point

CSHSE's parent association (MemberClick) maintains the canonical member directory. When a member logs into MemberClick and clicks "Self-Study Portal," they expect to land in CSHSE already authenticated — they should never see the CSHSE login screen. Today they do, and they have to remember (or invent) a separate password.

### Problem B — E2E tests rely on plaintext passwords in fixtures

CR-034's seed fixtures include a `userPassword` field that gets piped through `loginViaUI()` — the test browser actually types the password into the form. This works but:

- Plaintext passwords live in fixture JSON files in the repo (tagged "test-only" but still distasteful).
- The login form path is brittle to UI changes.
- It can't test "what does an SSO-authenticated session look like" because no such session exists today.

A single feature solves both: an API-key-authenticated SSO entry point. MemberClick uses it to ferry members in; the E2E suite uses it to acquire a session without typing anything.

## Decision (summary)

A new endpoint `POST /api/auth/sso-login` accepts a CSHSE-issued API key (HTTP header) and a member email (request body). It validates the key, looks up or auto-provisions the user, mints a session JWT, and returns either:

- A `sessionToken` (for programmatic callers like E2E), OR
- A 302 redirect with the session set as a same-site `httpOnly` cookie (for browser callers like MemberClick's pop-out).

API keys are managed in the existing Admin → API Keys settings page. A new `scope` field on the key record gates what each key can do (`'sso-login'` vs the existing `'general-api'`). The MemberClick integration receives a key scoped to `'sso-login'` only — it can never call anything else.

Keys are issued once at creation, hashed at rest, and revocable + rotatable from the settings UI. Every SSO entry is logged with the key id + email + caller IP for audit.

## Design

### Endpoint shape

There are TWO call shapes for the same logical entry point. The endpoint behaves based on the `Accept` header.

#### Shape 1 — Browser redirect (for MemberClick's "Self-Study Portal" link)

MemberClick generates a short-lived URL when a member clicks the link:

```
GET https://cshse.org/sso/start?ticket=<short-lived-ticket>
```

The `ticket` is an opaque ID MemberClick obtained via:

```http
POST https://cshse.org/api/auth/sso-ticket
x-cshse-api-key: <SSO-scoped key>
Content-Type: application/json

{ "email": "member@institution.edu", "intent": "self-study" }
```

→ returns `{ ticket: "abc123...", expiresAt: "..." }` (one-time, 60-second TTL).

When the browser arrives at `/sso/start?ticket=abc123...`, the CSHSE server:

1. Looks up the ticket; verifies it hasn't been consumed and hasn't expired.
2. Marks it consumed (atomic — the ticket cannot be replayed).
3. Resolves the user by email (provisions if allowed; see below).
4. Mints a session JWT, sets it as an `httpOnly`, `Secure`, `SameSite=Lax` cookie.
5. 302-redirects to the configured landing URL (default `/`).

**Why the ticket dance instead of putting the key in the URL?** API keys must never appear in URLs (they leak to browser history, referer headers, server access logs, screenshots). The ticket is a one-time random opaque value — leaking it after consumption does nothing.

#### Shape 2 — Direct API (for E2E + programmatic callers)

```http
POST https://cshse.org/api/auth/sso-login
x-cshse-api-key: <SSO-scoped key>
Content-Type: application/json
Accept: application/json

{ "email": "test-coordinator@example.test" }
```

→ returns:

```jsonc
{
  "sessionToken": "<JWT>",
  "user": {
    "id": "...",
    "email": "...",
    "role": "program_coordinator",
    "institutionName": "..."
  },
  "expiresAt": "..."
}
```

The E2E suite stores the `sessionToken` in `localStorage` (or sets the cookie directly) and proceeds with no UI interaction. The `loginViaUI` helper stays in the codebase for the few specs that exercise the login form itself; everything else moves to `loginViaSso(seed)`.

### API key model — extend the existing one

`server/src/models/APIKey.ts` already exists for the legacy n8n/general-API use. Extend its schema with:

```ts
scope: 'general-api' | 'sso-login';           // NEW; default 'general-api'
allowedRoles?: ('program_coordinator' | 'reader' | 'lead_reader' | 'admin')[];
                                               // NEW; auto-provision constrained to these roles
autoProvision: boolean;                        // NEW; default false
lastUsedAt?: Date;                             // already exists, ensure populated
revokedAt?: Date;                              // already exists
// NOTE: NO allowedEmailDomains field — per 2026-05-23 user direction,
// the allowlist is derived at request time from existing CSHSE users'
// email domains, not stored on the key. See "Auto-provisioning rules".
```

Key invariants:

- An SSO-scoped key can ONLY hit `/api/auth/sso-ticket` and `/api/auth/sso-login` — middleware rejects it on any other route with a 403 + `[sso-key-misuse]` log line.
- A general-api key can NOT hit either of the SSO endpoints.
- Cross-scope use surfaces clearly so a misconfigured caller is caught fast.

### Settings UI — admin-only

Existing route: Admin → API Keys (already implemented). Add to the "Create API Key" form:

```
Name:        [____________________]  (e.g., "MemberClick prod")

                              ↑

```

After Generate:

- Show the plaintext key ONCE in a copy-to-clipboard banner with the warning "This is the only time this key will be shown. Store it securely now."
- Persist only the bcrypt hash (already the pattern for the existing implementation; verify).
- Key id + scope + name + masked prefix (first 8 chars + `…`) appears in the list view.
- Per-key actions: View usage log (last 100 SSO logins), Rotate, Revoke.

### Auto-provisioning rules

Per user direction 2026-05-23 — "The list of email domains should be taken from the user table of the login. These users will have been invited into the CSHSE portal and this should be automatic." — there is NO admin-maintained domain allowlist. The allowlist is derived at request time from existing CSHSE users.

When `autoProvision: true` on the key AND the resolved email doesn't match any existing CSHSE user:

1. **Derive the live allowlist:** query the `User` collection for the distinct set of email domains where at least one user has `provisionedBy.type === 'invitation'` OR `provisionedBy.type === 'manual'` (i.e., a real human admin invited them, not another SSO autopop). This is the trusted-domain set.
   - **Why exclude SSO-provisioned users from the seed:** prevents self-reinforcing trust. If a single rogue SSO autopop accidentally created `user@badactor.com`, that user's mere existence shouldn't make `badactor.com` a trusted domain — the trust must trace back to an explicit admin invitation.
   - The query is cached per-import (~30s TTL) so high-traffic SSO doesn't hammer Mongo with the same distinct-aggregation.
2. The incoming email's domain MUST appear in the derived allowlist. If not, return 403 + `[sso-domain-not-yet-trusted]` log line. The error page tells the member: "Your institution has not yet been onboarded to CSHSE. Ask your CSHSE administrator to invite at least one user from your institution; you'll then be able to sign in via MemberClick."
3. Create a `User` record with the email, role = key's `defaultRole` (typically `program_coordinator`), `status = 'active'`, `passwordHash = null`.
4. Stamp `provisionedBy: { type: 'sso-key', keyId: ... }` for audit. NOTE this user is NOT added to the seed-domain set for #1 — only the first user at a new institution counts (the one invited via the normal flow).
5. Continue to session minting.

When `autoProvision: false` and the user doesn't exist:

- Return 404 + `[sso-user-not-found]` log line. Friendly error page.

**Onboarding workflow this creates:**

1. CSHSE admin invites a first PC at a new institution via the normal **Admin → Users → Invite** flow. Stamped `provisionedBy: { type: 'invitation' }`.
2. The invited PC accepts the invite + sets a password (the existing invitation flow). Their email domain is now in the trusted-domain set.
3. Any subsequent member from the same email domain can sign in via MemberClick SSO; CSHSE auto-creates their user with `provisionedBy: { type: 'sso-key' }`.
4. The admin never has to maintain a list of allowed domains; it grows naturally with the institution count.

**Edge case — admin removes the last invited user from an institution:** the domain falls out of the allowlist. New MemberClick SSO requests from that domain start failing with the "not yet onboarded" error. Existing SSO-provisioned users are unaffected (their session works; only NEW provisioning is blocked). Admin can re-invite to re-trust the domain.

### Audit logging

Every SSO ticket creation + consumption + direct sso-login attempt logs at INFO with:

```
[sso] event=ticket-created  keyId=abc  email=member@x.edu  ip=...  ticketId=...
[sso] event=ticket-consumed keyId=abc  email=member@x.edu  ip=...  ticketId=... outcome=ok
[sso] event=ticket-consumed keyId=abc  email=member@x.edu  ip=...  ticketId=... outcome=expired
[sso] event=sso-login       keyId=abc  email=member@x.edu  ip=...  outcome=ok
[sso] event=sso-login       keyId=abc  email=member@x.edu  ip=...  outcome=domain-rejected
```

These pipe to the existing error-logs admin export so admins can audit MemberClick traffic and detect anomalies (e.g., 100 SSO logins in 60 s from one IP — abuse).

### Rate limiting + abuse defenses

- Per-key: max 60 ticket creations per minute (legit MemberClick traffic stays well under).
- Per-IP at the `/sso/start?ticket=...` endpoint: max 30 ticket consumptions per minute (defeats brute-force ticket guessing — 60-second TTL on opaque random ticket already makes guessing infeasible).
- Bcrypt verification of the API key on every call (constant-time, ~100ms — acceptable for SSO; if it becomes a bottleneck, cache the hash→plaintext mapping in memory for active keys only).
- IP allowlist optional per key (turn on for MemberClick if their egress IPs are stable).

### Session JWT

Re-use the existing JWT signing used by `/api/auth/login` (same `JWT_SECRET`, same payload shape). The SSO endpoint shouldn't introduce a parallel session mechanism; it should produce the SAME session a password login produces. Downstream code (auth middleware, role checks, impersonation, etc.) doesn't have to know how the session was acquired.

JWT claims gain one new field:

```jsonc
{
  ...existing,
  "auth_method": "password" | "sso-key" | "invitation"
}
```

For audit purposes only. Downstream code ignores it unless it specifically needs to gate something (e.g., "you can't change your password if you logged in via SSO — your IdP owns it"). Not in scope for v1.

## E2E impact — the CR-034 simplification

Current state (CR-034 as proposed):

```ts
const seed = await seedFixture('wizard_review_minimal');
await loginViaUI(page, seed.userEmail, seed.userPassword);  // ← UI form interaction
```

New state with CR-042:

```ts
const seed = await seedFixture('wizard_review_minimal');
await loginViaSso(page, seed.userEmail);   // ← API call, no form
```

Where `loginViaSso(page, email)`:

1. POSTs to `/api/auth/sso-login` with the test-environment SSO key (read from `E2E_SSO_KEY` env var).
2. Receives the JWT.
3. Sets it as the session cookie on the Playwright page context.
4. Returns.

Wall-clock: < 100 ms (vs ~1.5 s for the UI form path). Removes the form-rendering brittleness entirely.

**Fixture cleanup:** `wizard_review_minimal.json` and its siblings drop the `password` field from `user`. The seed endpoint still creates the user (so its email exists for the SSO lookup) but no longer stamps a passwordHash. Existing `loginViaUI` continues to work for the few specs that explicitly test the login form (`01_login.spec.ts`).

## Threat model

| Threat | Mitigation |
|---|---|
| API key exfiltrated from MemberClick | Admin rotates the key in CSHSE settings; old key revoked instantly; MemberClick re-fetches new key from CSHSE admin |
| API key committed to public repo | bcrypt at rest + a startup scan for any string matching the key pattern in the repo (CI guard) |
| Replay of consumed ticket | Tickets are one-time; consumption is atomic via Mongo `findOneAndUpdate({_id, consumedAt: null}, {$set: {consumedAt: now}})` returning the old doc |
| Phishing — attacker tricks MemberClick admin into adding a malicious email to the SSO call | Allowed email domains restrict provisioning; audit log shows every successful SSO |
| Brute-force ticket guessing | 32 bytes of entropy in the ticket ID + 60s TTL + IP rate limit; effective infeasibility |
| Auto-provisioning grants too much access | New users default to `program_coordinator`; admin must elevate manually; `allowedRoles` on the key gates auto-provision |
| Stolen session JWT | Same protections as the existing password path: short JWT TTL, refresh required, httpOnly cookie |
| MemberClick admin's CSHSE account compromised → can issue new SSO keys | Existing admin-account security (passwords + MFA where supported); audit all key creations |

## Acceptance criteria

**Core auth (private-API minimum):**

1. Admin can create an API key with scope `sso-login`, tier, allowed email domains, autoProvision flag, and default role from Admin → API Keys → Create.
2. The plaintext key is shown exactly once on creation and never again. Key format `cshse_sso_v1_<32-char-random>`.
3. `POST /api/v1/auth/sso-ticket` with a valid SSO-scoped key and a known email returns a one-time ticket with 60-second TTL.
4. `GET /sso/v1/start?ticket=...` consumes the ticket, sets the session cookie, and 302s to `/`.
5. Re-using the same ticket returns 401 + clear RFC 7807 error body.
6. `POST /api/v1/auth/sso-login` with a valid SSO-scoped key returns a JWT directly (for programmatic callers).
7. An SSO-scoped key calling any non-SSO endpoint returns 403 with an audit log entry.
8. A general-api key calling either SSO endpoint returns 403 with an audit log entry.
9. Auto-provision creates a user with the correct role + status + audit fields when the email domain is allowed AND the email doesn't already exist.
10. Auto-provision rejects with 403 when the email domain is NOT in the allowlist.
11. Revoking an SSO key from settings causes subsequent sso-login attempts with that key to return 401 within 10 s of revocation.
12. Rotating an SSO key invalidates the old key and shows the new plaintext key once.
13. E2E test helper `loginViaSso(page, email)` works against `cshse-develop` and authenticates a fresh Playwright context in < 200 ms.
14. CR-034 fixtures no longer include `userPassword`; existing seed-driven E2E specs migrate to `loginViaSso` without behavior changes.
15. Audit log shows every ticket creation + consumption + direct sso-login with key id, email, IP, request_id, and outcome.

**Public-API additions:**

16. All endpoints are URL-versioned (`/api/v1/...`). Calling an unversioned legacy URL returns 410 Gone with a clear migration message.
17. `GET /api/v1/openapi.json` returns a valid OpenAPI 3.1 spec describing every public endpoint. Spec validates against the OpenAPI schema.
18. A redoc-generated public docs page is reachable at the agreed docs host and updates on every CR-042 deploy.
19. Multiple keys can coexist for different partners. Settings UI lists every key with tag, scope, tier, last-used, status — searchable + filterable.
20. Per-key dashboard shows the last 100 sso-login events + a request-rate graph + success/error breakdown for the last hour.
21. Per-key tier (`dev` / `standard` / `partner` / `enterprise`) enforces the rate-limit ceilings from the tier table; exceeding returns 429 with `Retry-After` header.
22. Suspending a key (faster than revoke) causes subsequent calls to return 503 `[sso-key-suspended]` within 5 s; unsuspending restores within 5 s.
23. Every error response follows RFC 7807 Problem Details shape with `type`, `title`, `status`, `detail`, `instance`, `request_id`.
24. CORS is explicitly NOT enabled for the direct sso-login endpoint — preflight returns 405. Verified by an automated test.
25. A sandbox environment (`sandbox.cshse.org`) serves the same API surface against an isolated user DB; sandbox keys clearly labeled in admin UI.
26. Status page (`status.cshse.org`) shows uptime for `auth-sso-v1`; incidents annotated.
27. Deprecation: when `/v2/` ships, `/v1/` responses include `Deprecation: true` + `Sunset: <date>` headers; `/v1/` continues to work for at least 12 months.

## Public-API requirements (added per 2026-05-23 clarification)

These items apply on top of everything above. A private integration could ship without them; a public API cannot.

### URL versioning

All public endpoints carry a major-version prefix:

- `POST /api/v1/auth/sso-ticket`
- `POST /api/v1/auth/sso-login`
- `GET  /sso/v1/start?ticket=...`

A breaking change creates `/v2/`. `/v1/` continues to work for at least 12 months after `/v2/` ships; deprecation warning header (`Deprecation: true`, `Sunset: <date>`) added when the deprecation window opens. Documented sunset dates published on the public docs page.

### OpenAPI 3.1 spec

The endpoints + request/response shapes live in `server/src/openapi/sso-v1.yaml`. The spec is served at `GET /api/v1/openapi.json` (public, no auth required). A `redoc-static` page is published to `https://docs.cshse.org/sso/v1/` (or equivalent — pick the docs host with the user). Partners' OpenAPI tooling generates client SDKs directly.

### Public-facing documentation page

Beyond the OpenAPI spec, a human-readable docs page covers:

- "Getting started — request an API key" (CSHSE admin contact + what they'll ask for: integration name, expected traffic, redirect URL, allowed email domains).
- The ticket flow (sequence diagram).
- The direct-login flow (sequence diagram).
- Error codes table.
- Rate limits per tier.
- Versioning + deprecation policy.
- Audit + monitoring (what partners will see in their CSHSE admin view; what we log).
- A small "test it now" curl example using a sandbox key.

### Multi-tenant key management

Each external integration gets a separate API key. The settings UI must scale beyond one key:

- Search / filter the keys list by name, scope, last-used, status.
- Tag each key with the partner name + a free-text description.
- Per-key usage dashboard (last 30 days): requests/minute graph, success-vs-error rate, top error codes, recent IPs.
- "Suspend" toggle (faster than full revoke) for incident response — partner's key still exists, returns 503 with `[sso-key-suspended]`.

### Rate-limiting tiers

Hardcoded rate-limit constants don't scale across partners (a small partner's normal traffic could trip MemberClick's allotted ceiling). Per-key configurable tiers:

| Tier | Ticket-creates/min | Sso-login direct/min | Audit-log retention |
|---|---:|---:|---:|
| `dev` | 10 | 10 | 7 d |
| `standard` | 60 | 60 | 30 d |
| `partner` | 300 | 300 | 90 d |
| `enterprise` | 2000 | 2000 | 1 y |

Tier set per-key at issuance; changeable by admin. MemberClick gets `partner` at launch.

### Per-key audit + dashboard

For every key, the admin settings page exposes:

- Live request count for the last hour (refresh every 30 s).
- Last 100 sso-login events with timestamp, email, IP, outcome, latency.
- Aggregate stats: success rate, top emails, top source IPs, top error codes.
- Anomaly alerts: surge detection (>3σ above the last-30-days baseline triggers an inline warning).

A future CR can pipe this to an external observability stack (Datadog/Honeycomb); for now in-app dashboards are enough.

### CORS

The ticket flow uses a browser redirect, so CORS isn't relevant for it. The direct-login flow is server-to-server (no browser) and explicitly does NOT allow browser-origin calls — `Access-Control-Allow-Origin` is omitted; preflight returns 405. Prevents a phishing site from harvesting CSHSE sessions even if a key leaks to a malicious browser-side context.

### Versioning of the API key itself

The key string format is `cshse_sso_v1_<32-char-random>`. The `v1` prefix tells humans + tooling which key generation it is. Old `v0` keys (if any from the legacy n8n integration) are auto-migrated to `v1` on first use.

### Standard error response shape

Every public endpoint returns errors in a uniform shape (matches RFC 7807 Problem Details):

```json
{
  "type": "https://docs.cshse.org/sso/errors/key-revoked",
  "title": "API key revoked",
  "status": 401,
  "detail": "The API key used has been revoked by an administrator. Contact CSHSE support to obtain a replacement.",
  "instance": "/api/v1/auth/sso-login",
  "request_id": "req_abc123"
}
```

`request_id` is the same ID logged on the server side — partners can quote it when filing support tickets.

### Sandbox environment

A non-production environment at `https://sandbox.cshse.org/api/v1/...` for partners to integrate against without affecting real users. Same API surface; isolated user database; sandbox-issued keys clearly labeled in CSHSE admin (`<sandbox>` chip). MemberClick integrates against sandbox first; flips to production only when their test plan passes.

### SLA + status page

Public status page at `https://status.cshse.org/` shows uptime for `auth-sso-v1`. Target SLA: 99.5% per month (matches the underlying Railway uptime). Incidents annotated.

## Appendix — MemberClick administrator integration walkthrough (non-programmer)

Per user direction 2026-05-23 — "show the steps that a memberclick administrator would have to program inside memberclick to build the login to the CSHSE application. Assume the administrator is NOT a programmer."

The MemberClick admin uses only point-and-click UI inside MemberClick. They do NOT write JavaScript, do NOT host a backend, do NOT compute cryptographic signatures by hand. CSHSE provides everything pre-built; the admin pastes URLs and one verification string. Total time: under 15 minutes once both admins are at their keyboards.

### Why this works without the admin writing code

The challenge in the original ticket flow design (Shape 1 in the Endpoint shape section) is that issuing a ticket requires a server-side API call with a secret key — something a MemberClick admin can't do from a templating UI. We solve this by providing a **MemberClick Relay** endpoint owned by CSHSE that accepts a simpler "launch URL" the admin can paste, and validates the request using three layered defenses (Referer header + IP allowlist + email-domain allowlist) instead of an in-URL signature.

The API key (the actual secret) never leaves CSHSE. The MemberClick admin only ever sees a non-secret integration ID + a verification token.

The admin can review the current auto-derived list in the integration package — it auto-updates as new users are invited. Example of what the admin sees, read-only:

     ```
     https://cshse.org/sso/v1/from-memberclick?integration=mc-7f3a2b&email={{MEMBER_EMAIL}}&t={{TIMESTAMP}}
     ```
   - **Verification token** — a short text string the MemberClick admin pastes into one field on their side as a one-time proof of ownership:
     ```
     cshse-verify-2026-05-23-9XK4mP7t
     ```
   - **Test URL** — used in Part 3 below to verify the wiring works:
     ```
     https://cshse.org/sso/v1/from-memberclick/test?integration=mc-7f3a2b
     ```
7. Click **Send to MemberClick admin** to email the package securely (CSHSE-side email with a one-time-view link, expires in 7 days).

The admin does NOT see the actual API key in this package — CSHSE manages the secret internally. The `integration` ID (`mc-7f3a2b` above) is a public identifier that ties the launch URL back to the key in CSHSE's database.

#### Part 2 — MemberClick admin (in the MemberClick admin UI), ~7 min

The MemberClick admin opens the integration package email from CSHSE and follows three steps inside their own MemberClick admin panel.

**Step A — Paste the verification token to prove site ownership.**

1. Sign in to MemberClick as an admin.
2. Navigate to **Settings → Organization Profile → Custom Fields** (or **Site Metadata** depending on MemberClick plan).
3. Find or create a custom field named exactly: `cshse_verification`
4. Paste the verification token (`cshse-verify-2026-05-23-9XK4mP7t`) as the value.
5. Save.

This step lets CSHSE confirm (via a public GET on MemberClick's API) that the MemberClick site really is the one CSHSE thinks it is — defeats an attacker who guesses the launch URL and tries to use it from a different MemberClick instance.

**Step B — Add the launch button to the Member Portal.**

1. In MemberClick admin, navigate to **Member Portal → Quick Links** (or **Custom Links** / **Member Resources** depending on plan).
2. Click **Add Link** and fill in:
   - **Display name:** `Open Self-Study Portal`
   - **Icon:** (pick one — e.g., a document icon)
   - **Link target:** paste the **Launch URL template** from the CSHSE package, but replace the merge-field placeholders with MemberClick's native merge syntax:
     ```
     Original: https://cshse.org/sso/v1/from-memberclick?integration=mc-7f3a2b&email={{MEMBER_EMAIL}}&t={{TIMESTAMP}}

     With MemberClick merge syntax:
     https://cshse.org/sso/v1/from-memberclick?integration=mc-7f3a2b&email=%%MEMBER_EMAIL%%&t=%%NOW%%
     ```
     (MemberClick's exact merge syntax varies by plan — the CSHSE integration package includes a one-page cheat sheet covering the three common syntax variants: `%%FIELD%%`, `{{field}}`, `[field]`.)
   - **Open in:** New window
   - **Visible to:** Members only (or whichever roles should have access)
3. Save.

**Step C — Confirm the wiring.**

1. Sign out of MemberClick admin.
2. Sign back in as a regular MemberClick member (use a test member account if available).
3. Find the new **Open Self-Study Portal** link in the member portal.
4. Click it.
5. A new tab opens to the CSHSE Self-Study Portal, already signed in as the member.

If anything fails, CSHSE returns a plain-English error page like:

> **We couldn't sign you in via MemberClick.**
>
> Reason: the request came from a network address we don't recognize for this integration.
>
> What to do: ask your MemberClick admin to share the rejected IP address (`203.0.113.42`) with your CSHSE administrator. We'll update the allowlist.

No HTTP status codes, no JSON — written for the member, with a clear "what to do next" line.

#### Part 3 — Verification ping (CSHSE admin), ~2 min

1. CSHSE admin returns to **Admin → API Keys → MemberClick integration** in the CSHSE UI.
2. Click **Verify Now**.
3. CSHSE makes a server-to-server GET to MemberClick's public org-metadata endpoint (no MemberClick auth needed for this; it's a public profile field), reads the `cshse_verification` field, confirms it matches the token issued in Part 1 step 6.
4. Status flips from `Pending Verification` to `Verified`.
5. The launch button starts accepting real traffic. (Before verification, the relay endpoint returns "integration not verified yet" so a leaked URL can't be used.)

### Security model — what protects each step

The relay endpoint is a coordinated check of four independent signals — an attacker would need to defeat ALL of them simultaneously:

| Defense | Configured by | Defeats |
|---|---|---|
| **Verification token on the MemberClick side** | CSHSE issues, MemberClick admin pastes | An attacker who guesses the launch URL but doesn't control the MemberClick site |
| **Referer header validation** | CSHSE admin lists MemberClick site domains | Off-MemberClick page that copy-pastes the launch URL into a phishing link |
| **IP allowlist** | CSHSE admin lists MemberClick egress IPs | Anyone not coming from MemberClick's infrastructure |
| **Email-domain allowlist (auto-derived)** | Built-in — derived at request time from the email domains of CSHSE users provisioned via the normal invitation flow. No admin maintenance. | Even a compromised MemberClick can't issue logins for emails at institutions CSHSE has never onboarded |
| **Timestamp freshness** | Built-in (CSHSE rejects `t=` older than 5 min) | Replay of an old launch URL captured from logs or browser history |
| **One-time relay-token-to-session exchange** | Built-in | A captured launch URL can be used at most once; subsequent uses return "already consumed" |
| **Audit log** | Built-in | Detection (not prevention) — every relay launch is logged with IP + Referer + email + outcome; admin can spot anomalies |

If any one of these signals fails, the request is rejected with the plain-English error page above + a detailed audit log entry on the CSHSE admin side.

The actual API key never crosses the network — it lives in CSHSE's database, signing requests internally when the relay endpoint validates the launch URL. The MemberClick admin's "secret" is just the verification token, which proves site ownership but doesn't grant any other authority.

### What this looks like to a member (the end user)

1. Member signs into MemberClick as they always do.
2. Member portal home page now shows an **Open Self-Study Portal** button (placed by the admin in Part 2 Step B).
3. Member clicks it. A new tab opens.
4. The CSHSE Self-Study Portal appears, already signed in. No second login screen.
5. (Behind the scenes, in under 200ms: MemberClick rendered the launch URL with the member's email + current timestamp; the browser GET hits the CSHSE relay endpoint; CSHSE validates all four signals + the verification token; CSHSE either looks up the existing user or auto-provisions a new one; CSHSE sets the session cookie + 302-redirects to `/`.)

If the member's MemberClick session has expired between MemberClick and CSHSE — i.e., they were idle for hours and MemberClick logged them out before they clicked the button — MemberClick handles the re-login on its side; CSHSE never sees that case.

## Out of scope

- SAML / OIDC federation — MemberClick uses a custom integration, not standard SSO protocols. If a second IdP comes along we'll add OIDC then.
- Single sign-OUT — when the MemberClick session ends, the CSHSE session continues until its JWT expires. SLO is non-trivial and not requested.
- Per-user MFA on SSO accounts — defer to MemberClick; CSHSE trusts MemberClick's auth strength.
- API key usage limits beyond the rate limits above (concurrent session caps, etc.).
- Self-service key generation by non-admins.
- Partner self-service onboarding (partners contact CSHSE admin to get a key for v1; self-service is a v2 feature).
- Webhooks back to partners on user events (e.g., "this user just completed their self-study"). Separate CR if requested.
- OAuth 2.0 / OpenID Connect compliance — the API is intentionally simpler. If we need OAuth later, it's a new endpoint family alongside.

## Risk

- **API key leakage from MemberClick.** The biggest residual risk. Mitigation: rotation is fast + audit log makes anomalies visible.
- **Allowed-domains misconfiguration.** A typo could let in or shut out users. Mitigation: settings UI shows a preview "Currently 247 CSHSE users match these domains; 12 would be auto-provisioned"; admin reviews before save.
- **Session-JWT cookie scope.** Setting cookies on `cshse.org` vs `cshse-develop.up.railway.app` requires careful `Domain` attribute on the cookie. Verify against MemberClick's actual launch URL during integration testing.
- **Race condition on ticket consumption under parallel browser tabs.** Atomic `findOneAndUpdate` handles it.
- **Backwards compatibility with the existing apiKeys controller.** Extending the schema is additive; the existing n8n-style keys default to `scope: 'general-api'` and continue to work. Migration: a one-line update on existing records to stamp the default scope.
